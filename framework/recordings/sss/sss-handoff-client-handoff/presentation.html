Run it locally

1. You need

Node 20 or later, and npm.

PostgreSQL 14 or later on localhost port 5432.

On Windows, clone to a short path.

2. Build and test

Clone the public repository, then in backend: npm ci, npm run build, npx jest.

Then npm ci in frontend.

3. Start the API

createdb sss_demo, then npm start in backend.

It applies all 28 migrations itself.

Settings are environment variables, set by name

Database

DATABASE_HOST, DATABASE_PORT, DATABASE_NAME, DATABASE_USER, DATABASE_PASSWORD.

The local defaults are development values only.

First staff

CASE_MANAGER_EMAILS and ADMIN_EMAILS set up the first case manager and administrator.

Secrets and AI

JWT_SECRET signs sign-in tokens. ANTHROPIC_API_KEY turns on AI answers; without it the assistant shows policy passages.

Never paste a value anywhere.

When it misbehaves

Check health first

Open /health on the API. database "ok", "down" or "starting".

Down: data routes answer 503 and recover by themselves.

Read the alerts

Administrators open Observability. Each alert has a runbook entry in docs/RUNBOOK-ALERTS.md.

Sign-in failures

"Invalid token" often means an expired token or a wrong JWT_SECRET. The older troubleshooting guide is a day-one document; trust the runbook.

What the new owner owns

You own

The tests, the migrations, the access rules and the runbook.

Every new route needs its access rule in the same change.

You do not own

Real applicants, real policy, or any claim of production. This is a case study.

Open gaps, parked

A hands-on screen-reader test and an independent security test. AWS GovCloud is closed.
