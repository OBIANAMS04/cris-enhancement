# Stakeholder update: speaker notes (PREP-4)

For Obi only; never shown to the audience. **3 minutes speaking**; 2 minutes of questions are separate.
**Audience:** Ali Muwwakkil (Managing Director), the decision-maker; Ram Katamaraja.
**Purpose:** in 20 seconds Ali knows what is on track and what is not, and he leaves having made one decision.
**Portal:** on PREP-4 → Learn, the presentation type is **Stakeholder update** (selected 16 Nov).
**Framing:** CRIS is a Colaberry rehearsal case study. TxDOT is not consulted, so nothing is "waiting on TxDOT";
open points are closed by working assumptions from TxDOT's published terms, each labelled on screen and kept in one file.

## The script (about 320 words: about 2:30 at 130 words a minute, leaving room to breathe inside 3:00)

**Slide 1 (0:00 to 0:15).** "Ali, the Crash Records update. The build is done and on track for the twenty-fourth.
The case-study recordings were late: they were due on the thirtieth of October. The introduction and the slides are
handed in; the two videos go in before Demo Day."

**Slide 2, what is done (0:15 to 1:15).** "What is done. All sixteen stories are verified by the portal: fifty of
fifty acceptance criteria, eight hundred points. The evidence I'd point to is the rehearsal: one browser walk that runs
all sixteen stories in the order I'll demo them, from an empty workspace, and passes. Seventy-three unit tests pass
too. Demo prep is finished: the run-of-show script, the rehearsal, and the demo-day presentation. Rehearsing found
three real problems, a refusal message drawn off screen, a doubled word, and a Documents banner that contradicted the
training rule, and all three are fixed."

**Slide 3, what is stuck (1:15 to 1:55).** "What is stuck. Only one thing, and it is mine: the two videos in my own
voice, the working-system demo and the final showcase. They are recorded locally, with the server running, before the
twenty-fourth. Nothing is waiting on TxDOT. This is a rehearsal, so TxDOT is not consulted: where the solicitation's own
values are not public, the build uses working assumptions from TxDOT's published terms: the scoring weights, the
required documents, the closing time, the service levels. Each one is labelled on screen and kept in one file."

**Slide 4, the proposed next action (1:55 to 2:40).** "My recommendation: accept those working assumptions as the
baseline for the case study, and on Demo Day show the evaluation with the proposed weights, labelled as proposals,
which the page already does. The scoring rules work the same with any weights: weighted scores, a score far from the
others flagged, a correction that keeps the original. So the demo proves the method. In a live engagement, the client's
weights replace one file and nothing else changes."

**Slide 5, the decision (2:40 to 3:00).** "So one decision. Option A: accept the working assumptions and close the
case study with the evaluation shown, labelled as proposals. Option B: keep the evaluation step out of Demo Day.
I recommend A. Which one?"

Then stop talking.
